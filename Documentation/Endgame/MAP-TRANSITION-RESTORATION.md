# 地图切换：恢复初始生命周期

## 范围与基线

恢复 `GameBootstrap` 的切图准入、原生 `switching` 门、队列处理、
`TransitionTo` / `Fade` 与 ready 时机，以仓库最早可核对的提交
`f8d8885`（Initial source release targeting 1.6.0）为行为基线。

`fa41a5b` 是恢复前的已部署源码对照，不是初始基线。
`f8d8885` 的代码标注恢复官方 1.5.8 方法；本次源码对照不能代替对用户早期运行安装包的校验。

本次不增加或修改协议字段。客户端首次完整建图后仍按原协议发送
`SavePos(entered=1)`。服务端应正确消费首次 ready，并在目标所有权完成后
发送必要的第一轮实体快照。

## 撤回的切图行为

- 撤回 `78ce2b0` 后增加的跨整段淡出串行状态机和 portal 排队逻辑。
- 撤回“没有重新建图，却在同落点队列分支再发送一次 entered=1”的补偿。
- 撤回本轮未发布的异步地图读取、额外输入/出站门控与 token、失败锁定、
  延后地板首刷和新增计时方案。

原生后来收到的真实 `0x803a` 仍按原始生命周期处理，没有增加全局按地图和坐标
丢弃传送的逻辑。应修正服务端交接竞争，而不是用丢弃真实传送来隐藏重复加载。

## 四项明确保留的例外

1. **同步单次地图字节交接**

   保留 `fa41a5b` 已有的 `PreparedMapSource`。在原同步预读位置读取一次，
   后续建图消费同一数组；不增加线程、yield、等待或确认，也不是长期地图缓存。

2. **旧场景经验视觉清理**

   在确认将退旧后、原淡入开始前，清理明确属于旧场景的待显示经验提示和活跃经验飘字。
   不改变真实经验值，不清除归属不明的新通知，不改变 ready 时机。

3. **失败安全检查与重试**

   目标和回滚均要求 `worldRoot != null && window != null && window.Built`。
   只有半建根对象时，不误报加载成功。同步预读抛异常或资源缺失时，恢复旧图字段
   并清除切图锁；若是本地门触发，只在离开门区后再次进入时允许重试，避免每帧重试。

4. **最终退出取消协程**

   最终退出时停止未完成地图协程、清待切队列并复位黑幕，避免登出后重新建图。
   普通地图切换不经过这一退出取消路径。

## 保留的功能

- 私有秘境传送门仍直接走服务端的下一层路由，不先加载真实世界地图再拉回。
- 真实 NPC 入口、状态图标、经验视觉归属以及其他非切图功能不随生命周期还原而回退。
- 原协议的场景快照发布逻辑保留；每次真正完成建图仍需要自己的首次 ready。

## 云端验证

使用已配置的 Mono / Roslyn 工具链：

```sh
python3 Tests/WorldEntry/run-map-transition-contract.py --compare-baseline
```

该脚本编译执行实际生产 `BuildWorldCore`、切图迭代器、`ReportPos`、`Fade`、
sky 与传送门代码，并使用确定性的 Unity 替身。

验证结果：

- 恢复版：96 个断言，25 个场景。
- 直接从 git 读取的 `f8d8885` 原始生产协程：54 个断言，12 个场景。
- 9 条正常流程逐帧轨迹一致：建图次数、ready 次数、当前地图、收包门、黑幕状态。
- 首次建图完成后才发 ready；其后的首轮实体保留到淡出完成。
- 加载期间同落点排队不会补第二条 ready。
- 连续地图、同图真实传送、不同权威目的地排队、异常回滚和缺失资源均覆盖。
- 半建目标或半建回滚不能误报 ready。
- 建图前后退出，以及停止迭代器是否触发 Dispose 两种情况，均不会复活旧协程。
- 私有秘境门不会触发真实地图预加载。
- 同步字节单次消费单独校验；读取次数优化不参与正常时序比较。

## 验证边界

上述测试证明源码控制流与消息确认时机，不等于 Unity / Metal 的实际渲染或帧时间测试。
原始同步 I/O、强制 GC 和 Unity 对象构建保留，不据此承诺实机零卡顿。
服务端真实踩门与首次 ready 交接的回归，应另行验证；不能用客户端替身测试代替。

## 修复前的有界极端调度历史对照（服务端 27291d0）

```sh
python3 Tests/WorldEntry/run-map-transition-contract.py --stress
python3 Tests/WorldEntry/run-map-transition-contract.py --stress-original
```

这两项保留服务端来源分类修复前的行为，**预期以非零退出复现历史兼容问题**；
它们不是最终服务端候选的回放，后面的真实包回放才检验本轮修复。
它们驱动真实客户端生产迭代器，使用两条 FIFO 队列安排上下行与主线程帧边界；
不在同步建图内部伪造网络回调，也不让刚启动的协程在同帧再次恢复。
服务端队列行为在此是明确的调度模型，应与真实 session/router 回归配对阅读。

- 恢复版：290 种有界调度、1281 项安全检查，其中 100 种命中同一类重复建图窗口。
- f8d8885 对照：252 种调度、1203 项检查，同样 100 种命中该窗口；另暴露两项资源失败重试问题。
- 恢复版额外覆盖 38 个退出/替换生命周期边界；两项资源失败问题已通过小范围安全修正关闭。
- 连续 A→B→C、同地图同落点的 24 种真实后续传送序列，以及 server-first 单传送、
  首 ready 上行等待、快照等待和掉帧配置均纳入矩阵。客户端没有实例字段，
  同图不同实例的服务端归属需由真实 session/router 测试另证，不能由此客户端替身推出。

这 100 种调度是**一个问题的不同时间组合**，不是 100 个独立缺陷，
也不能据此判定原官方客户端有问题。它揭示原客户端与修复前自建服务端的一处兼容窗口：

1. 客户端本地建完，发送首 ready。
2. 服务端此前因踩门已经发送首 0x803a，但它仍在下行途中。
3. 客户端在淡出时才收到该 0x803a，按原行为开始第二次建图。
4. 紧随其后的首轮实体快照在 switching 期间未被接纳；第二次 ready 又触发补全快照。

两个方向各自仍保持 TCP FIFO。这种交叉不能仅靠“提前 ready 收据”覆盖；
这正是本轮服务端普通门来源分类修复针对的窗口。历史诊断保留失败，不以更改预期或
重新加入大切图状态机把它改成通过。

普通门本地预测有前提：本地存在匹配 JSON 门、非 custom map、非命令门、非秘境接管，
且玩家没有死亡/打工/禁足/同乘等提前返回状态，也不在出生门内抑制或已传送锁中。
此次历史调查时，生产 MapLink 的资源重载只读 teleport_links JSON；云端未取得该真实表和资源包，
不能声称数据库所有普通门均与客户端表一致。任务寻路、跟随与插件普通导航仍共享
原生位移和门检测尾部，不能据此扩展为对所有特殊传送的保证。

服务端的配对生产证据是 `server/internal/session/client_map_ready_test.go` 中
`TestClientMapReadyFIFOActorScheduleMatrix`（在服务端仓库运行）：
ready 先于 source Move 时为 0 个 0x803a 加 1 次首快照；handoff 先于 ready 时，
即使确认已不会丢失，仍为 1 个首 0x803a 加 1 次首快照。
这是修复前 crossing 诊断的真实生产前提；当时不能将单次加载标为通过。

每批消息只有在真实客户端迭代器发出相应 ready 后才能投递，不能凭空追加第二次快照。

- 实际 sender 证明普通门只执行本地回调，预建前没有目标 `entered=0`、门户请求或强制
