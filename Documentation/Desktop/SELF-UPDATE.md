# Desktop whole-application updates

Status: implementation and managed/filesystem contract tests, not a signed or released Player. macOS and Windows require their actual platform acceptance runs before distribution. This updates the entire application; no C# hot-update assembly or remote script is loaded.

## Operator build boundary

The desktop resource-free Player includes the updater from the same approved source revision. It does not download an updater from dispatch. Build the helper locally with an already-installed official stable .NET SDK 8 or newer:

```sh
scripts/build-desktop-updater.sh windows /absolute/new/windows-updater
scripts/build-desktop-updater.sh macos /absolute/new/macos-updater
```

The script pins an available stable SDK (8 or newer), targeting net8.0, publishes self-contained single files, and never installs SDKs, signs, uploads or deploys. Windows output is `DesktopUpdater.exe` (x64); macOS output contains `DesktopUpdater-osx-arm64` and `DesktopUpdater-osx-x64`. The selected SDK can restore the net8.0 targeting/runtime packs from the official package source if absent; this is a build dependency, not an SDK installation. No separately installed .NET runtime is required on the player's computer. The .NET host may extract its bundled runtime into its standard per-user cache.

Supply this exact flat directory to the resource-free build lane through `FFO_DESKTOP_UPDATER_DIRECTORY`. The lane writes the identity marker and copies helpers under StreamingAssets/DesktopUpdater. See the resource-free build documentation for the approved stable application ID, dispatch endpoint and platform signing identity inputs. The marker is `ffo-desktop-install.json` at the Windows application root or `Contents/Resources/ffo-desktop-install.json` inside a macOS bundle. It binds schema 1, platform, application version, stable install ID, relative executable, macOS Team ID and Windows signing certificate SHA-256.

The installed marker selects the existing publisher policy; dispatch cannot turn it off. A nonempty macOS Team ID requires the matching signed identity and successful Gatekeeper assessment. A nonempty Windows certificate digest requires Authenticode chain validation and that exact certificate. The helper and application must follow the same approved release signing flow. Certificate rotation or a changed Team ID requires a separately planned/manual transition: an update cannot silently weaken or replace the installed signing policy. No private key enters the marker, dispatch or helper build command.

The current no-paid-certificate distribution uses empty signing fields and a production HTTPS bootstrap. It does not require Developer ID or Authenticode merely to prepare an update. macOS still requires a valid ad-hoc code signature, matching application identifier and bundle version; this integrity seal is not a paid publisher identity. Windows still verifies its product version. The existing formal build lane continues to require configured signing identities; this change does not relabel a development build as a signed release. Neither mode disables Gatekeeper, SmartScreen/Defender or other OS policies. Mac trust validation does not add, rewrite or remove quarantine metadata on a candidate; existing marks remain. Windows MOTW behavior is unchanged. The OS can still prompt or reject launch.

Quarantine is a separate download policy, not a side effect of trust validation. Apple describes the non-sandboxed opt-in model and background self-updates in [WWDC19, Advances in macOS Security, 5:12](https://developer.apple.com/videos/play/wwdc2019/701/?time=312); [LSFileQuarantineEnabled](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/LaunchServicesKeys.html) defaults to false. The helper therefore does not manufacture a new `0083` marker at each validation. This does not delete existing attributes, disable system protection, bypass an existing rejection or change normal LaunchServices launching. ZIP extraction is not a contract to propagate the archive file's extended attributes to extracted files. Test fresh, independently built candidates without clearing marks from prior acceptance artifacts; keep fixture output outside protected user-document directories. These source-level rules do not establish successful native launch on their own.

Only package immutable output matching the selected installed publisher policy using `scripts/ci/package-desktop-update.py`. Its root is exactly the dedicated Windows application folder name or macOS `.app` name. The archive is standard ZIP, not ZIP64, a self-extracting executable, MSI, DMG, PKG or tar. The build packager intentionally imposes Python's conservative standard ZIP limit below 2 GiB per file/archive, at most 65,534 entries and 64 MiB central directory, with at most 16 GiB expanded. This is sufficient for resource-free Players; game resource payloads are distributed separately. Links/special files are refused; any approved flattening must precede signing. macOS executable Unix permission bits must be present in ZIP metadata. Renaming an installed application folder/bundle changes the required archive root and is not an automatic-update migration.

The normal package downloader also accepts legacy installer extensions for manual installation. The new automatic helper accepts only a ZIP satisfying this contract.

## Player flow

1. The existing bounded, no-redirect download transport saves the complete package in the private ClientPackages cache. It verifies the dispatch version, length and SHA-256, and revalidates before handing off.
2. The player copies its bundled updater to `persistentDataPath/DesktopUpdates/<job-id>`, outside the application being replaced. It records the canonical install/data/package paths and parent PID/start identity. Only the running executable matching the installed marker can request this handoff.
3. The independent helper runs without elevation. It locks the installation, rechecks the complete package bytes, validates ZIP paths/entry limits/types, and extracts into a fresh sibling directory on the same filesystem as the application. User data, downloaded resources and package caches must be disjoint from the application tree. The helper never copies over a live application file.
4. Package marker, executable product/bundle version, install ID and signing policy must match the requested update. macOS always checks `codesign --verify --deep --strict` and application identifier/version; configured Team IDs additionally require team matching and `spctl --assess --type execute`. Windows always checks product version; configured certificate digests additionally require WinVerifyTrust and certificate matching. Windows retains Zone.Identifier behavior. Mac validation leaves existing quarantine metadata untouched and does not manufacture a new marker. The helper does not turn off platform security.
5. Only after successful preparation does the UI offer “退出并安装更新”. The user must click it. The helper waits for the original process to exit and rejects another running copy before replacing anything. Preparation cancellation, parent exit without confirmation, a 30-minute unanswered preparation or a 5-minute failed exit preserves the installed app.
6. Before committing, every staged file is hashed again and additions/deletions are rejected. The helper revalidates trust. It renames the old directory to a unique sibling backup, then renames the staged application into place. These individual same-filesystem renames are atomic; the pair is a journaled transaction, not a single atomic operation. If rename, trust or a confirmed terminal OS launch failure occurs, it restores the old directory when possible and retains the failed new application. A possibly running new app is never intentionally renamed for rollback: if launch is indeterminate or a matching process is still running/uninspectable, both versions and the recovery journal are retained instead.
7. LaunchServices (`open`) or Windows ShellExecute opens the new application with normal OS policy. An accepted start request alone is not success. The helper waits up to 30 seconds for the actual executable process, then requires a short three-second survival window; observed early exit triggers rollback when the application is stopped. A timeout, pending OS prompt or uninspectable/translocated launch is indeterminate, not a success or proof of safe rollback. Dismiss pending OS prompts, close all application copies, and use the retained recovery command if needed. This check is not a full game-health or login check, and does not detect a later crash. A failed success-receipt write never rolls back a confirmed running application. The retained backup is never automatically deleted.

If the helper is absent, the installed layout is unmarked/renamed, the install location is unwritable/translocated, signature or trust validation fails, a platform policy blocks the launch, or the package is not a supported ZIP, the game offers an explicit manual folder-opening fallback. It never executes the downloaded file automatically, requests administrator access or tells the player to bypass a security warning. Already distributed helpers with unconditional Developer ID/Authenticode requirements cannot update themselves through a package they reject: they run from the installed application, not from dispatch or the downloaded ZIP. Those installations require one manual installation of a corrected complete application containing the new helper. Changing dispatch alone cannot repair them. This manual transition may use a rebuilt 1.0.2 package, distinguished by its source commit/build identity; it does not require choosing a new product version. The normal automatic update comparison remains strictly increasing, so it will not discover another 1.0.2 build as an upgrade. Keep rebuilt artifacts identifiable rather than claiming that the old and corrected builds are identical.

Resource activation retains its existing all-files-verified boundary. An unmatched platform/application-version resource map cannot open the game, even if a stale “ready” root exists. Required application updates remain available without a compatible resource map. When resources finish successfully and no optional/required application-update choice remains, the bootstrap opens the title/login page automatically through the same verified-entry guard. It does not submit login credentials or change protocol/authentication versions.

## Failure and recovery

Every prepared job retains `request.json`, `transaction.json`, status text and its bundled helper in the player's private DesktopUpdates directory. The transaction contains only local paths and public application identity. Download caches, interrupted staging, old backups and failed new directories are retained rather than recursively deleted. This trades disk usage for recovery; cleanup must be an explicit later maintenance action.

A crash or power loss between the two renames can leave the application path missing. The old app remains at the recorded sibling `.update-backup-<job-id>` path. Quit all copies, then run the retained helper with the original job request:

```text
DesktopUpdater.exe --recover "C:\...\DesktopUpdates\<job-id>\request.json"
DesktopUpdater-osx-arm64 --recover "/.../DesktopUpdates/<job-id>/request.json"
```

Choose the retained helper matching the OS/process architecture. Recovery validates the journal/path/backup identity, rejects a live application, takes the same installation lock and restores the backup. If a new application exists, it is moved to a `.update-failed-<job-id>` sibling, never deleted. The helper does not elevate to recover protected directories. A filesystem failure during rollback can require manual recovery from the retained backup; logs/status name that condition. The updater does not promise power-loss durability of every directory rename on every filesystem, nor recover user data from an independent disk failure.

## Verified and unverified boundaries

Run:

```sh
source Documentation/tools/activate-dotnet-test-toolchain.sh
Tests/DesktopUpdater/run-desktop-updater-contract.sh
python3 Tests/DesktopUpdater/test_helper_build.py
Tests/ClientUpdate/run-package-ui-contract.sh
```

The desktop tests compile all actual helper source and exercise real ZIP parsing, full-file hashes, path rejection, identity/pin mismatch, staged mutation, cancellation, same-volume swaps, injected failures, retained user files and journal rollback. Both Windows/macOS archive fixtures are produced by the actual Python build packager and then consumed by the C# updater. Native OS trust and process APIs are replaced in these portable tests; signed and empty-pin trust branches, bounded startup confirmation, indeterminate launch retention, safe rollback and success-receipt failure are exercised with injected boundaries; no synthetic executable is run. The four UI test builds cover Android, Windows, macOS and unsupported desktop fallback including an unmatched resource-map gate.

The original contract runs used the official .NET 6 runtime, Roslyn 4.8 and recovered Unity API reference profile. The no-paid-certificate fix was also compiled and tested with the installed .NET 8 runtime/reference assemblies and SDK compiler: 422 updater checks, all four package-UI variants, 36 Python build/packaging tests and four helper-build tests passed. These are not Unity Player tests. They do not prove .NET 8 self-contained publication, IL2CPP stripping, Windows/macOS process inspection, native signature APIs, notarization, antivirus/SmartScreen behavior or actual Player relaunch. Release acceptance must build the exact source tag locally and test initial install/update on each platform, protected/read-only/translocated targets, signature rejection, two running copies, cancellation, disk full, parent crash, deliberate termination between renames and rollback. Keep settings and existing verified resource hashes before/after as evidence. No production deployment is implied by source tests or packaging.

SDK selection follows [Microsoft’s version-selection policy](https://learn.microsoft.com/en-us/dotnet/core/versions/selection): a newer SDK can target earlier runtimes, and a self-contained publication includes the selected runtime. SDK-10 selection is covered by a mocked command test; the actual SDK-10 native publication still requires a local build.

## Required platform acceptance for the no-paid-certificate fix

These checks are still pending until performed on authorized Windows/macOS test systems; cloud contract tests do not establish them. Do not use a user's computer for development implicitly.

1. Inspect the actual installed and candidate markers. Keep application/executable identity stable and both signing fields empty for the current distribution. A manual corrected 1.0.2 build may retain the product version; the subsequent automatic-update acceptance candidate must have a strictly newer test version. On Mac confirm the actual app/helper ad-hoc signatures and executable permissions, not just synthetic fixtures.
2. Manually install the corrected full application once to replace the old helper, retaining user settings and downloaded resources. A same-version rebuild is valid for this manual step. Then test a second, higher-version candidate through the corrected helper; this acceptance test does not allocate a future production release version. Existing old-helper rejection and the explicit manual fallback must also be verified.
3. With normal Gatekeeper/SmartScreen/Defender settings and quarantine/MOTW intact, verify download, prepare, explicit exit/install, process confirmation and relaunch on each platform. Record prompts or App Translocation honestly; an accepted launcher exit code is not proof of success.
4. Verify explicit OS rejection and immediate process exit restore the old app/resources when no copy is running. Verify a pending system dialog, uninspectable process or timeout retains both versions without an installed receipt; after dismissing dialogs and quitting copies, verify --recover restores the old app/resources.
5. Recheck signed-mode rejection for wrong Team ID/certificate, invalid signature and removal of a nonempty installed pin. Also verify cancellation, corrupt/identity-mismatched ZIP, two running copies, unwritable install location and retained resource/settings contents. No OS warning bypass is part of acceptance.
